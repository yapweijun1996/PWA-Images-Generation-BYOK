## Concurrent project views and interruption

On November 24 Singapore time, loopback Chrome 158.0.8127.37 and Playwright WebKit 27.2 ran the exact [published `49388bd` artifact](https://github.com/yapweijun1996/PWA-Images-Generation-BYOK/actions/runs/45239647736) in separate disposable two-tab contexts. The submitting tab showed `Generating` while a locally intercepted provider response was held. The second tab showed no job until it reloaded. When the response was released, the second tab stayed on `Generating` even after IndexedDB showed `succeeded` with one version.

Both engines repeated the scenario on the corrected local production build `2026-11-23T18:47:24.129Z`. Both tabs reached `Generating` while the response was held. The passive tab then showed `Completed`, decoded the selected image and downloaded an exact match of the fixture PNG. Reloading the passive tab during the held request did not acquire the active request's lock. Each run intercepted one generation request.

Chrome also completed the original project's job after the submitting tab created and switched to a different project. The other project remained free of the job state. A separate Chrome run returned HTTP 503 and the passive tab showed `Result unconfirmed` without creating a version. In WebKit, closing the submitting tab while the response was held and reloading the observer produced `Result unconfirmed`, zero versions and one total provider attempt. The fixture did not issue an actual OpenAI request. This covers a browser-tab close and observer reload rather than operating-system termination.

On [published build `e9c076f`](https://github.com/yapweijun1996/PWA-Images-Generation-BYOK/actions/runs/45242606194), live Chrome 158 and loopback WebKit 27.2 and Firefox 159 repeated the two-tab completion and original PNG comparison. Chrome then went offline, rejected an uncached request, reopened the completed job and downloaded the identical PNG again. On the exact retained artifact, WebKit repeated the tab-close interruption with one intercepted request and zero versions. In a separate Chrome fixture, an invalidation signal made a newly persisted `queued` record visible in the observer and produced zero intercepted requests with both views left open. Opening a project can still resume a durable queued job under the existing lock rules.

### Recovery in an already open view

Chrome 158.0.8127.37 and Playwright WebKit 27.2 replayed the exact retained `e9c076f` artifact. An intercepted provider request was held, the submitting tab closed, and the browser's lock query confirmed release. With the second tab left open, both its interface and IndexedDB still reported `running` after two seconds.

On the corrected local build `2026-11-23T19:00:31.286Z`, Chrome, WebKit and Firefox 159 each kept the job `running` while the submitting tab held the lock. After it closed, the existing observer displayed `Result unconfirmed` without a navigation. Each context recorded one intercepted provider attempt and zero versions. In Chrome, a four-image submission with two existing observers produced one uncertain item and three visible unsent items in both observers, with all four states committed together.

In the normal WebKit completion control, the observer retained the succeeded state, one version and the original PNG's SHA-256. A separate Chrome check confirmed that an observer waiting for the lock cancelled its wait when it switched to another project. The original request completed once. Fixtures intercepted all provider requests. The interruption used a browser-tab close while a peer remained open.

[Published build `8d319a6`](https://github.com/yapweijun1996/PWA-Images-Generation-BYOK/actions/runs/45245075066) reproduced the four-image scenario in public Chrome. Two already-open observers reached one uncertain item and three visible unsent dependents with no navigation, no version and one intercepted request. WebKit and Firefox repeated the single-job recovery against the retained release artifact on loopback.

The public Chrome build also completed one actual low-quality `gpt-image-2.6-flare` request. The test forwarded the browser's image request to OpenAI with the credential confined to the local test process. OpenAI returned HTTP 200. The observer saw `Generating` and then `Completed`, decoded the 1024 × 1024 PNG, and downloaded it with SHA-256 `9503d441779219197145763221e6d461e4f5b1feb192264cd3c3185768a95841`. The forwarding setup exercises real output and the queue's completion behavior. Earlier browser-direct tests supply the CORS evidence.
